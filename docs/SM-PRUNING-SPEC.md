## 1. Overview

The pruning system is a background maintenance service that scores every fact on a 6-signal staleness composite, archives candidates to a cold DB, removes them from the hot DB, and reclaims space via VACUUM. It is resumable, quality-gated, and loses zero data.

## 3. Staleness Scoring Formula

```
Staleness(fact) = 0.20 × T_decay
                + 0.25 × A_low
                + 0.15 × G_low
                + 0.15 × C_low
                + 0.10 × S_low
                + 0.15 × R_high
```

All signals normalized to [0,1] where 1.0 = most stale (highest prune priority).

| Signal | Weight | Computation |
|---|---|---|
| **Temporal Decay** | 0.20 | `T = 1 - e^(-λ_t · Δt)` where λ_t varies by namespace |
| **Access Frequency** | 0.25 | `A_low = 1 - 1/(1 + count·e^(-λ_a·Δt_last))` — frequently accessed facts resist pruning |
| **Graph Connectivity** | 0.15 | `G_low = 1 - Degree(fact)/MaxDegree` — isolated facts prune first |
| **Content Importance** | 0.15 | corrections/policies/skills=0.1, durable_fact=0.5, observations/inferences=0.9 |
| **Source Authority** | 0.10 | verified_source=0.2, observation=0.5, inference=0.9 |
| **Semantic Redundancy** | 0.15 | candle cosine >0.98 → redundant pair. Lower-quality fact scores 1.0, retained scores 0.0 |

### Per-namespace decay constants

| Namespace | λ_t | Threshold |
|---|---|---|
| `ephemeral_inference` | 0.5 | 0.50 (aggressive) |
| `general` | 0.1 | 0.75 |
| `coding` | 0.05 | 0.85 |
| `research` | 0.08 | 0.80 |
| `instruction_policy` | 0.01 | 0.90 (never prune) |
| `durable_facts` | 0.01 | 0.90 |

## 4. Pruning Algorithm — 8-Phase Pipeline

```
SCAN → CLASSIFY → ARCHIVE → DELETE_EDGES → DELETE_FTS → DELETE_VEC → HARD_DELETE → VACUUM
```

Each phase writes its completion to `prune_runs.phase`. If interrupted, resume starts at the first incomplete phase.

### Phase details

1. **SCAN**: SELECT all facts with `lifecycle_state='active'`. Counts only.
2. **CLASSIFY**: Compute staleness score for each. Filter by per-namespace threshold. For redundant pairs (cos >0.98), mark the lower-quality one `R_high=1.0`.
3. **ARCHIVE**: Copy candidate facts + their vectors + their edges to a cold archive DB (separate `.db` file). Store blake3 checksums in `prune_tombstones`. Set `lifecycle_state='archived'`.
4. **DELETE_EDGES**: For archived facts, remove graph edges. Edge policy: `RemoveIfLeaf` — remove only if no other edges reference either endpoint.
5. **DELETE_FTS**: Delete from `facts_fts` by rowid.
6. **DELETE_VEC**: Delete from `fact_vectors` by fact_id.
7. **HARD_DELETE**: DELETE FROM facts WHERE lifecycle_state='archived'. Commit tombstone records.
8. **VACUUM**: `VACUUM INTO` a temp file, then swap. Prefer during low-activity window.

## 5. Automation & Scheduling

**Recommended: systemd timer** — `semantic-memory-prune.timer` + `.service`

- Runs weekly (Sunday 03:00 local)
- Dry-run first run (no deletes, reports what would happen)
- Emits structured receipt → `system-health-monitor`
- On failure: aborts, marks `prune_runs.phase='aborted'`, does NOT touch live data

### Safety

- **Pre-pruning snapshot**: `sqlite3_backup_init()` to a temp file, or `VACUUM INTO` before pruning
- **Dry-run mode**: `--dry-run` computes scores and reports candidates without any writes
- **Quality gate**: Before pruning, run 50 representative queries. After pruning, re-run. If recall@k degrades >5%, abort and roll back.
- **Rollback**: Restore from pre-pruning snapshot, or `UPDATE facts SET lifecycle_state='active' FROM prune_tombstones`

## 6. Quality Gate

```
BEFORE: Run 50 representative search queries → baseline recall@k
PRUNE:  Execute at threshold T
AFTER:  Re-run same 50 queries → post-prune recall@k
GATE:   If (baseline - post) / baseline > 0.05 → ABORT + ROLLBACK
        Else → COMMIT + VACUUM
```

Queries selected across all namespaces, weighted by access frequency.

## 7. Agent Graph Integration

The quality gate runs as an agent graph for parallel verification:

```
Graph: sm-prune-quality-gate
  Node 1: pre-prune-recall → runs 50 queries, records baseline
  Node 2: execute-prune → runs the pruner (dry-run or real)
  Nodes 3-5 (parallel): post-prune recall checks across 3 query partitions
  Node 6: synthesize → compares baselines, produces go/no-go decision
```

This lets 150 queries run in parallel across 3 workers instead of sequentially.
